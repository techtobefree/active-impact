# Push — notifications on the phone, with the app closed (design)

> SOCIAL.md S8 shipped an in-app bell and deferred push. This un-defers it: when
> somebody you follow RSVPs or checks in, their phone buzzes — no native app, no
> app store, no third-party service.
>
> Read alongside [SOCIAL.md](./SOCIAL.md) (whose notification rules this reuses
> exactly) and [FRONTEND.md](./FRONTEND.md) (the service worker).
>
> Source of intent: `../intent.md` § "Notify their phone".

---

## 1. What this actually is

Web Push. The server sends an encrypted payload to the push service the browser
nominates (Google's for Chrome, Mozilla's for Firefox, Apple's for Safari); that
service wakes our **service worker** in the background — the app need not be open,
or even running — and the worker calls `showNotification()`, which posts to the
OS tray with sound and vibration like any other notification.

**No APK.** No Firebase account, no OneSignal, no cost, no vendor. We hold a
VAPID key pair and talk to whatever endpoint each browser hands us.

## 2. The iOS constraint, which shapes the whole feature

| Platform | Works? | Must the PWA be installed? |
|---|---|---|
| Android / Chrome | Yes | No — a plain tab can subscribe |
| **iPhone / Ipad — Safari** | Yes, **iOS 16.4+** | **Yes. Mandatory.** `PushManager` does not exist in an iOS Safari tab at all |
| Desktop Chrome / Edge / Safari | Yes | No |

So for a large share of volunteers, *"Add to Home Screen"* is not a nicety — it is
the on-switch. A settings toggle that silently does nothing on iPhone would be the
worst possible outcome, so the notifications screen **detects this case by name**
and shows the Share → Add to Home Screen steps instead of a dead switch (§6).

## 3. Decisions

| # | Decision | Rationale |
|---|---|---|
| **P1** | **VAPID keys are generated by the app on first use and stored in the database** (`app_keys`), not configured. | OVERVIEW D16 keeps the config surface at two knobs, and this deployment model ships a tarball — a key the founder must generate by hand is a feature that silently never works. Keys must also be **stable** (they are baked into every subscription), so generating per-boot is out; the database is the one place that already survives restarts, redeploys and restores. |
| **P2** | **One row per device** (`push_subscriptions`), keyed by the push endpoint. | People have a phone and a laptop, and the same person subscribing twice from one browser yields the same endpoint — so the endpoint is the natural identity. |
| **P3** | **A dead subscription is deleted, not retried.** 404/410 from the push service means the browser threw it away (uninstalled, cleared data, expired). | Self-healing garbage collection with no cron. Anything else accumulates junk that slows every send. |
| **P4** | **Who gets pushed is EXACTLY who the bell counts** — a follower of the actor, `notify_activity` on, not blocked, not themselves. One rule, two transports. | The badge and the buzz disagreeing would be a bug nobody could explain. `app/activity.py` already owns that rule; push asks it the same question. |
| **P5** | **Sending happens off the request path**, on a small thread pool, after the transaction commits. | A check-in must not wait on three HTTPS round trips to Google, and a push failure must never roll back a check-in. Nothing is queued or persisted: a push that fails is lost, which is the correct severity for "your friend arrived somewhere". |
| **P6** | **The bell stays.** Push is an additional transport, not a replacement. | It is the only thing that works for a denied permission, an iPhone that never installed, or a desktop browser with notifications off — and it is still the record of what happened. |
| **P7** | **Subscribing is the switch.** No second preference: `notify_activity` gates everything, and the presence of a subscription for this device decides whether *this device* buzzes. | Two overlapping switches is how settings screens become confusing. |
| **P8** | **Permission is asked from a tap, never on load.** | A denied permission is **permanent** — the browser will not re-prompt, and the user must dig into site settings to undo it. Asking cold, before anyone knows what the app is, spends that one chance for nothing. |
| **P9** | **`pywebpush` is added to requirements.** | The payload is ECDH + HKDF + AES-GCM to a spec with known footguns. This is the one place in this codebase where "write it ourselves" would be reckless rather than lean. First new backend dependency since launch; recorded here deliberately. |

## 4. Schema delta

```sql
-- Small, boring key/value for things the app mints for ITSELF (as opposed to
-- config, which is env). Today: the VAPID pair.
CREATE TABLE IF NOT EXISTS app_keys (
  name       TEXT PRIMARY KEY,
  value      TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- One row per DEVICE. `endpoint` is the push service's URL for that browser and
-- is the subscription's identity.
CREATE TABLE IF NOT EXISTS push_subscriptions (
  id         BIGSERIAL PRIMARY KEY,
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  endpoint   TEXT NOT NULL UNIQUE,
  p256dh     TEXT NOT NULL,          -- the device's public key (from the browser)
  auth       TEXT NOT NULL,          -- the device's auth secret (from the browser)
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_push_subscriptions_user ON push_subscriptions(user_id);
```

`endpoint` is UNIQUE across all users on purpose: if a phone is handed to somebody
else who signs in, the subscription re-points to the new owner rather than
notifying the previous one.

## 5. API

| Endpoint | Notes |
|---|---|
| `GET /api/push/key` | `{public_key}` — the VAPID application server key the browser needs to subscribe. Generated on first call and stable thereafter |
| `POST /api/push/subscribe` | `{endpoint, p256dh, auth}` → **201** `{subscribed: true}`. Idempotent per endpoint (re-subscribing re-points it to me) |
| `POST /api/push/unsubscribe` | `{endpoint}` → `{subscribed: false}`. Idempotent |
| `GET /api/push/status` | `{subscribed}` for a given `?endpoint=` — so a device can tell whether *it* is registered without guessing from browser state |

## 6. The screen (`#/notifications`)

One block, showing exactly one of five states — the whole point being that a
person always learns *why* they will or will not be buzzed:

| State | What we show |
|---|---|
| Supported, no permission yet | **Notify me on this phone** button (asks permission on the tap — P8) |
| Subscribed | "This device will buzz" + **Turn off on this device** |
| Permission denied | An honest explanation that the browser is blocking it, and that it must be re-enabled in site settings — we cannot re-ask |
| **iOS, not installed** | **The nudge.** "Add Active Impact to your Home Screen to get notifications on your iPhone", with the literal steps: tap **Share**, then **Add to Home Screen**, then open it from there. No dead toggle |
| Anything else unsupported | One honest line; the in-app bell still works |

The nudge is deliberately not a nag banner on every screen: it lives where somebody
has already expressed interest in notifications by opening the notifications page.

## 7. What a notification says

Title: the actor. Body: what they did, where. Tapping opens that event.

```
Ana Fields
is going to Riverside Park Cleanup          → #/events/42
```

Payloads are encrypted end-to-end (only that browser can decrypt), so naming
people in them is no more exposing than the feed they already see.

`notificationclick` focuses an existing tab if one is open rather than piling up
new ones, and navigates it to the event.

## 8. Invariants

| # | Invariant |
|---|---|
| **P-I1** | The VAPID public key is stable across restarts and redeploys — a rotation would silently break every existing subscription. |
| **P-I2** | Push recipients are exactly the bell's recipients: followers of the actor, `notify_activity` on, not blocked, never the actor. |
| **P-I3** | A subscription rejected as gone (404/410) is deleted, and one failure never affects another recipient's send. |
| **P-I4** | Re-subscribing the same endpoint moves it to the current user rather than duplicating it. |
| **P-I5** | Sending never happens inside the transaction that recorded the activity, and a push failure never fails the action that caused it. |
| **P-I6** | An unsupported or uninstalled browser is told *which* case it is; no screen offers a switch that cannot work. |

## 9. Deliberately deferred

Digests and quiet hours · per-kind push preferences (the bell's one switch covers
it) · notifications for anything but `rsvp`/`checked_in` · retrying a failed send ·
delivery receipts · badging the app icon (`setAppBadge`) — a nice follow-on, not
needed to answer "can you buzz my phone".
